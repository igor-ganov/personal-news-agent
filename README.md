# Личный агент

Android-приложение для двух задач сразу:

1. **Выжимка по источникам.** Тема описывается словами, агент сам подбирает источники,
   а дальше собирает дайджесты за день, неделю, месяц или год — по кнопке или по расписанию.
2. **Развитие навыка.** По теме собирается программа на выбранный срок с выбранной
   интенсивностью; план можно поправить до запуска. Дальше по плану пишутся лекции со
   схемами, ссылками и отсылками к тому, что происходит в теме прямо сейчас, плюс тесты
   для самопроверки.

Темы вложены рекурсивно: у темы есть подтемы, у подтем — свои подтемы. Подтема
наследует фокус родителей, поэтому её материалы сразу учитывают общую рамку.
Программы можно строить на основе других программ — тогда лекции не повторяют
пройденное, а продолжают его и ссылаются на прежние занятия.

## Стек

Tauri 2 + Astro + Lit, TypeScript. Логика — чистые функции и структуры, разработка
через тесты. Вся UI-часть — веб-компоненты, без фреймворка и без гидратации.

## Устройство

```
packages/core      Чистый домен: типы-структуры и функции над ними. Никакого I/O.
packages/agent     Порт ContentProvider + реализации: Claude API и офлайн-заглушка.
packages/storage   Порт «прочитать/записать строку» + адаптеры, кодек и миграции.
packages/app       Стор поверх редьюсера, трекер задач, сценарии.
packages/ui        Презентационные компоненты на Lit: значения внутрь, события наружу.
packages/auth      Аккаунты и ключи доступа: порт платформы, клиент API, сессия.
apps/mobile        Astro-шелл, экраны-контейнеры, оболочка Tauri, нативный плагин.
services/api       Worker на Cloudflare: WebAuthn, сессии, документ состояния.
```

Зависимости идут строго в одну сторону: `ui` и `agent` знают только про `core`,
`app` связывает всё вместе, `apps/mobile` — единственное место, где что-то знает
про платформу.

Несколько решений, которые стоит знать заранее:

- **Ошибок-исключений в домене нет.** Функции возвращают `Result`; сообщение для
  пользователя появляется на границе сценария.
- **Редьюсер тотальный.** Действия несут уже провалидированные значения, поэтому
  `dispatch` не может завершиться неудачей, и UI не обрабатывает такие случаи.
- **Время и идентификаторы инжектируются.** Домен не читает часы сам — отсюда
  детерминированные тесты.
- **Черновик плана не хранится в сторе.** Пока пользователь правит план, это ещё
  не его данные; в стор он попадает при запуске программы.

## Как это работает

**Источники.** По описанию темы агент ищет, что стоит читать, и предлагает список.
Дальше он пополняется сам, но с двумя ограничениями: источник в блеклисте не
возвращается никогда, а источник, который пользователь добавил или отредактировал
руками, не переписывается. Блеклист уходит и в сам поиск (`blocked_domains`), и в
слияние результатов — на случай, если модель предложит его снова.

**Дайджесты.** Окно считается либо «скользящим» (последние сутки/неделя/месяц/год —
то, что даёт кнопка «что нового за…»), либо календарным — для регулярных сводок.
В запрос уходят только активные источники: приглушённые остаются в списке, но в
выжимку не попадают.

Каждый собранный дайджест остаётся в истории вместе с содержимым: новый не
затирает предыдущий, а встаёт первым в список над ним. Свежесобранный
открывается сразу — за этим и нажимали кнопку, — но любой прошлый доступен в
один тап. Хранится до 20 дайджестов на тему и период (`DIGEST_HISTORY`);
ограничение существует потому, что состояние — один сериализуемый документ.

**Скилы.** Мастер собирает намерение, бюджет времени и список программ, на которых
строится новая. Полученный план редактируется как данные: каждое действие — значение
`PlanEdit`, которое применяет домен. После запуска занятия получают даты, а лекции и
тесты генерируются по одному, по мере надобности.

## Генерация идёт на сервере

Запрос к модели живёт минутами: план программы или лекция — это веб-поиск,
рассуждение и десятки тысяч токенов ответа. Раньше такой запрос выполнялся прямо
из WebView и умирал вместе с приложением: экран висел, а потом падал с ошибкой
API. Теперь он выполняется на сервере и существует как строка в базе.

Что из этого следует:

- **Приложение можно закрыть.** Запрос уже поставлен в очередь; результат
  приезжает, когда приложение откроют снова.
- **Видно с другого устройства.** Задание принадлежит аккаунту, а не телефону,
  поэтому «идёт генерация» и «сорвалось вот с такой ошибкой» видны везде, где вы
  вошли.
- **Ошибка не исчезает молча.** Упавшее задание остаётся с текстом ошибки, пока
  его не увидят и не уберут; сетевые сбои и лимиты сервер пробует повторить сам.
- **Дважды не оплатите.** На аккаунт живёт одно задание на ключ (`program:тема`,
  `lesson:занятие`) — это ограничение базы, а не проверка в интерфейсе.

Ответ применяется ровно один раз: лекция, тест и дайджест попадают в документ
состояния при первой же синхронизации, после чего задание удаляется. План
программы — исключение: он ждёт, пока пользователь его примет или отбросит, ведь
до этого момента это ещё не его данные.

Ключ API при сохранении уходит на сервер (в базе — зашифрованным) — иначе
серверу нечем генерировать. Без аккаунта приложение работает по-старому: запрос
идёт с устройства и живёт, пока живёт приложение.

Сам запрос к модели теперь потоковый (`messages.stream`): нестриминговый запрос
такого размера упирается в таймаут HTTP — это и была та самая ошибка API.

## Запуск

```bash
pnpm install
pnpm test          # 647 тестов
pnpm typecheck
pnpm dev           # http://localhost:4321 — приложение в браузере
```

Без ключа API приложение работает на офлайн-заглушке: все экраны и переходы живые,
материалы демонстрационные. Ключ вводится в настройках и хранится отдельно от
остальных данных — в документ состояния он не попадает.

### Android

Тулчейн, на котором собирается APK:

| Компонент | Версия |
| --- | --- |
| JDK | 21 |
| SDK Platform | android-34 |
| Build-Tools | 34.0.0 |
| NDK | 27.3.13750724 (r27d) |
| Gradle | 8.14.3 (обёртка приходит вместе с `tauri android init`) |

Установка с нуля:

```bash
# SDK: cmdline-tools распаковываются в $ANDROID_HOME/cmdline-tools/latest
sdkmanager --licenses
sdkmanager "platform-tools" "platforms;android-34" \
           "build-tools;34.0.0" "ndk;27.3.13750724"

rustup target add aarch64-linux-android armv7-linux-androideabi \
                  i686-linux-android x86_64-linux-android
```

Сборка:

```bash
. scripts/android-env.sh   # ANDROID_HOME / NDK_HOME / JAVA_HOME, с переопределением снаружи

pnpm android:init          # один раз: создаёт apps/mobile/src-tauri/gen/android
pnpm android:dev           # сборка и запуск на устройстве или эмуляторе
pnpm android:build         # release APK под все ABI
```

Для одной архитектуры — быстрее в разы:

```bash
pnpm --filter @pna/mobile exec tauri android build --apk --target aarch64
```

Gradle отдаёт APK **без подписи**, а неподписанный Android ставить откажется.
Выравнивание и подпись — отдельным шагом:

```bash
scripts/sign-apk.sh
```

Ключ ищется в `~/.pna-android/pna-release.jks` (переопределяется через
`PNA_KEYSTORE`, `PNA_KEYSTORE_PASS`, `PNA_KEY_ALIAS`) и намеренно живёт вне
репозитория. Заведите свой — обновления придётся подписывать тем же ключом,
иначе система не поставит их поверх установленного приложения:

```bash
keytool -genkeypair -v -keystore ~/.pna-android/pna-release.jks -alias pna \
  -keyalg RSA -keysize 4096 -validity 10000
```

Каталог `src-tauri/gen/android` не в репозитории: он целиком воспроизводится
командой `tauri android init`.

Собранный APK: `dev.ganov.pna`, minSdk 24, arm64-v8a, 6,8 МБ.

## Аккаунт и синхронизация

Приложение остаётся локальным: без входа всё работает ровно как раньше и никуда
не уходит. Аккаунт нужен, только чтобы носить свои темы между устройствами.

Пароля нет. Вход — по ключу доступа (passkey): закрытый ключ остаётся в хранилище
устройства, сервер знает лишь его открытую часть, а почта служит меткой аккаунта.
Подтверждение почты пока не делается — почтового провайдера нет, и адрес до
подтверждения не даёт никаких прав.

Что происходит при входе:

- **Данные есть только на устройстве** — они переезжают в аккаунт. Локальный
  документ при этом опустошается: иначе выход воскресил бы то, что уже живёт
  в аккаунте.
- **Данные есть только в аккаунте** — они просто открываются.
- **Данные есть с обеих сторон** — приложение спрашивает. По умолчанию предлагает
  объединить: ничего из сделанного не пропадает. При совпадении идентификаторов
  побеждает копия из аккаунта — её уже видели другие устройства.

Синхронизация — целиком документом с оптимистичной ревизией. Устаревшая запись
не проходит: сервер возвращает актуальный документ, клиент сливает его со своим
(на совпадениях выигрывает устройство — это то, что пользователь только что
сделал) и отправляет ещё раз.

Документ каждого владельца лежит под своим ключом, поэтому два аккаунта на одном
устройстве не видят данных друг друга, а токен сессии хранится отдельно от
документа — он учётные данные, ему нечего делать в том, что синхронизируется.

### Ключи доступа на Android

В WebView нет WebAuthn: ключами владеет системный менеджер учётных данных, и
дотянуться до него можно только из нативного кода. Отсюда плагин Tauri в
`apps/mobile/src-tauri/plugins/passkeys` — Kotlin поверх `androidx.credentials`.
Обе стороны обмениваются тем же JSON, что и WebAuthn, поэтому плагин ничего не
разбирает: options уходят как есть, подписанный ответ возвращается как есть.

Чтобы система признала связь приложения и домена, Worker отдаёт
`/.well-known/assetlinks.json` с отпечатком подписи APK. Отпечаток задан в
`services/api/wrangler.toml`; подпишете релиз другим ключом — обновите и его,
иначе вход по ключу перестанет работать:

```bash
keytool -list -v -keystore ~/.pna-android/pna-release.jks -alias pna | grep SHA256
```

## Сервер

```bash
cd services/api
pnpm wrangler d1 migrations apply pna --local   # локальная база
pnpm dev                                        # http://localhost:8787
```

Маршруты: `/auth` — вход по ключам доступа, `/state` — документ аккаунта,
`/jobs` — задания на генерацию, `/provider-key` — ключ API аккаунта.

Секреты воркера:

```bash
cd services/api
pnpm wrangler secret put PROVIDER_KEY_SECRET   # шифрует ключи аккаунтов в базе
pnpm wrangler secret put ANTHROPIC_API_KEY     # необязательный общий ключ
```

`PROVIDER_KEY_SECRET` обязателен, если ключ загружает приложение: без него
сервер отвечает `no_key_storage` и ключ не сохраняется. Смена этого секрета
делает сохранённые ключи нечитаемыми — их надо загрузить заново.

Новую таблицу заданий нужно накатить на боевую базу:

```bash
cd services/api && pnpm wrangler d1 migrations apply pna --remote
```

Крон `*/5 * * * *` подбирает задания, чей вызов умер на полпути; ночной прогон
чистит просроченные сессии и давно завершённые задания.

Публикация идёт из GitHub Actions (`.github/workflows/api.yml`) при изменениях в
`services/api` на ветке по умолчанию: проверки, миграции D1, деплой, health-check.

## Релизы

Готовый APK: [последний релиз](https://github.com/igor-ganov/personal-news-agent/releases/latest)
или напрямую из ветки `dist`:

```
https://github.com/igor-ganov/personal-news-agent/raw/dist/personal-news-agent.apk
```

Публикация устроена так, что ключ подписи в репозиторий не попадает. Репозиторий
публичный, а ключ в публичном репозитории означал бы, что кто угодно соберёт APK,
который Android примет как обновление установленного приложения.

Поэтому подпись ставится вне CI, а в ветку `dist` кладётся уже подписанный APK.
Пуш в неё запускает `publish-apk.yml`, который создаёт релиз встроенным
`GITHUB_TOKEN` — секретов этот путь не требует вовсе. Перед публикацией он
сверяет отпечаток подписи с тем, что отдаёт `assetlinks.json`, и предупреждает,
если они разошлись: тогда вход по ключу на Android не сработает.

Выложить новую сборку:

```bash
pnpm android:build && scripts/sign-apk.sh
apk=apps/mobile/src-tauri/gen/android/app/build/outputs/apk/personal-news-agent.apk
commit=$(git rev-parse --short HEAD)

git worktree add /tmp/dist dist && cp "$apk" /tmp/dist/
cd /tmp/dist && echo v0.1.1 > VERSION && echo "$commit" > SOURCE_COMMIT
git commit -am "dist: v0.1.1" && git push
```

`.github/workflows/android.yml` собирает APK на каждый пуш в основную ветку:
проект Gradle в репозитории не хранится и создаётся заново, SDK и NDK у раннеров
свои. Если ключ подписи есть в секретах — подписывает и обновляет релиз; если
нет — кладёт неподписанную сборку в артефакты прогона, а подписанный APK
приезжает через ветку `dist`.

### Включить полный пайплайн

```bash
scripts/setup-ci.sh
```

Одна команда кладёт в репозиторий все пять секретов, сверяет отпечаток ключа с
`assetlinks.json` и печатает, что получилось. Запускать её надо со своей машины,
где сделан `gh auth login`: секрет в репозиторий кладёт тот, у кого есть на него
права, и это единственный шаг, который нельзя выполнить изнутри репозитория.

После этого пайплайн делает всё сам:

| Событие | Что происходит |
| --- | --- |
| пуш в основную ветку | сборка APK, подпись, обновление релиза `v<версия>` |
| пуш тега `v*` | то же, но релиз с этим тегом |
| изменения в `services/api` | миграции D1 и публикация Worker |

| Секрет | Нужен для | Без него |
| --- | --- | --- |
| `CLOUDFLARE_API_TOKEN` | публикации Worker; права Workers Scripts Edit, D1 Edit, Workers Routes Edit | `api.yml` только проверяет код |
| `CLOUDFLARE_ACCOUNT_ID` | того же | то же |
| `ANDROID_KEYSTORE_BASE64` | подписи APK в пайплайне | APK собирается, но остаётся в артефактах прогона |
| `ANDROID_KEYSTORE_PASSWORD` | того же | то же |
| `ANDROID_KEY_ALIAS` | того же | то же |

Значения сборки (`PUBLIC_PNA_API_URL`, `PUBLIC_PNA_DIAGRAMS`) заданы прямо в
`android.yml`: они не секретны, и в файле их видно вместе с остальным.

## Размер бандла

| Сборка | Размер `dist` | Стартовый чанк |
| --- | --- | --- |
| `PUBLIC_PNA_DIAGRAMS=off pnpm build` | ~440 КБ | 243 КБ (65 КБ gzip) |
| `pnpm build` (по умолчанию, со схемами) | ~3.9 МБ | те же 243 КБ |

Разница — Mermaid. Он подгружается динамически и на старт не влияет, но внутри
пакета место занимает. Если схемы не нужны, соберите с `PUBLIC_PNA_DIAGRAMS=off`:
условие сворачивается на этапе сборки, Mermaid выпадает из бандла целиком, а лекции
показывают исходник схемы вместо картинки.

SDK Anthropic тоже вынесен из стартового чанка — он загружается при первом запросе
к модели, а не при открытии приложения.

## Тесты

```bash
pnpm test                    # всё
pnpm vitest run --project core
pnpm vitest --project ui     # watch
```

Домен и сценарии тестируются на детерминированных часах и счётчике идентификаторов;
провайдер — на поддельном клиенте, без сети; компоненты — в happy-dom.

Ключи доступа проверяются программным аутентификатором (`@pna/auth/testing`): он
делает то же, что связка ключей телефона — заводит ES256-ключ, подписывает
challenge и отдаёт тот же JSON. Отдельный набор тестов доказывает, что настоящий
ключ и этот от сервера неотличимы, после чего им же гоняется сквозной сценарий
против живого API:

```bash
cd services/api && pnpm wrangler dev --local   --var RP_ID:localhost --var ALLOWED_ORIGINS:http://localhost:8787   --var PROVIDER_KEY_SECRET:test-secret

PNA_API_URL=http://127.0.0.1:8787 PNA_API_ORIGIN=http://localhost:8787   pnpm vitest run --project api
```

Этот же набор проверяет задания: постановку, единственность живого задания на
ключ, внятную ошибку без ключа API и удаление обработанного задания.

Отдельно — проверка, что воркер действительно доходит до модели: с заведомо
неверным ключом задание обязано завершиться её ошибкой, а не тишиной. Она ходит
в сеть, поэтому включается отдельно:

```bash
PNA_LIVE_MODEL=1 PNA_API_URL=http://127.0.0.1:8787   PNA_API_ORIGIN=http://localhost:8787 pnpm vitest run --project api
```

Без `PNA_API_URL` эти тесты пропускаются, и обычный прогон остаётся офлайновым.

Одна особенность окружения: happy-dom теряет маркеры Lit, если шаблон начинается или
заканчивается биндингом на верхнем уровне. Поэтому шаблоны компонентов обёрнуты в
один корневой элемент — в браузере это ни на что не влияет, а тесты остаются
честными.
